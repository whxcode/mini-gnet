# 多会话与后台任务

一个 App 管理多个打开的会话，统一持有一份运行配置。每个会话拥有自己的聊天记录、输入框和任务状态，不保存配置或客户端。
切换会话只改变正在查看的对象，不关闭记录文件，也不停止正在执行的任务。

会话（session）是一段持续的聊天及其上下文；任务（task）是一次普通提问触发的执行，可以包含多次模型调用和工具调用。
一个会话可以先后执行多个任务，不同会话可以同时执行任务。`/new` 只创建会话，发送问题后才启动任务。
`/sessions` 列出当前 App 已打开的会话及任务状态，不是历次任务列表。
`/resume` 加载历史会话；若已经打开，则切回原会话。恢复聊天记录不会重新执行历史任务。

## 使用

- `/new`：创建并切换到新会话，原任务继续运行。
- `/sessions` 或 F2：打开会话列表，上下选择、Enter 切换、Esc 返回。
- `/sessions 1`：直接切换到编号 1，也可以指定完整会话 ID。
- `/ps 2`：快速切换到编号 2，与 `/sessions 2` 使用同一个 handler；`/ps` 打开列表，Esc 返回。
- Alt+← / Alt+→：在已打开会话间切换；Alt+N 新建会话。终端拦截快捷键时可使用命令。
- `/resume`：恢复磁盘上的历史；已经打开的记录直接切回，不重复创建任务或写入者。
- `/stop`：停止当前会话正在执行的任务，并取消全部等待任务。Ctrl+C 在会话有执行或等待任务时也执行此操作。
- `/exit`：退出程序。还有任务运行时，Enter 确认停止全部任务并退出，Esc 返回。

后台会话结束后，当前界面单独显示“会话 N 已完成/失败/已停止 · /ps N 查看”，直到切回查看；顶部和会话列表也显示状态。
无需切回，后台就会收完模型输出并保存聊天记录。切回只是展示已有结果，不会启动或恢复执行；后台的完整正文不会混入当前会话。

每个会话只有一个消费协程，同时只执行一个任务。运行期间再次提交问题会进入队尾，最多等待 16 项；队列满时立即提示并保留草稿，不阻塞输入。界面单独显示等待数量及下一项提问。
等待队列只存在内存中，不支持重启恢复；提问轮到执行时才保存到聊天记录，避免当前任务提前看到后续问题。
草稿及光标在快捷切换、F2 菜单切换后仍然保留。输入框随内容增长，最多占用终端允许的空间。
界面使用普通终端模式，消息、状态和输入框依次排列；短对话不补空白行，不把输入框固定在屏幕底部。
标题和状态合并在顶栏，模型/目录与快捷键降低亮度；角色标题用颜色区分，正文统一浅色。输入框用边框和略亮底色与聊天正文分开。
多个会话以带边框的栅格卡片排列，当前卡片使用亮色边框。○ 空闲、◌ 执行中、✓ 已完成、× 错误、■ 已停止，● 新结果表示尚未查看的后台结果。
栅格随窗口宽度调整为 1–4 列，最多两排；会话较多时展示当前会话所在的一组，编号保持不变。高度不足时收起卡片，仍可用 `/ps 编号` 或 F2 切换。
内容超过终端可见高度后，可用 PgUp/PgDown 查看较早记录，不显示滚动条。

## 顺着代码阅读

`main.go` 只在启动时检查一次 stdin/stdout 是否为终端：终端进入 `App.Run`，管道进入 `App.RunPipe`。
App 不保存 `interactive` 字段；交互界面、会话状态和命令 handler 不再判断运行模式。

先看 `app.go` 的 `App.Run`：读取输入 → 查找命令并调用 handler → `enqueueTask` 入队 → 继续读取输入。

再看 `session.go` 的 `Session.Run`：从 `taskQueue` 取出一项 → 标记开始 → 同步调用 `RunTask` → 继续取下一项。这里不为每个任务启动 goroutine。
`workspace.go` 的 `attachSession` 只在创建或首次恢复会话时执行一次 `go s.Run()`，切换回已有会话不会再启动消费协程。

最后看 `agent.go` 的 `Session.RunTask`：先保存本次提问，再按顺序执行：

1. 在请求处用任务配置创建临时 `net.Client`，再通过 `client.OpenStream` 请求模型。
2. `stream.Next` 读取每段文字，直接更新所属 Session；读完关闭响应流。
3. 保存完整回答。
4. 没有工具调用就结束；若 Python 仍需修复则继续有限次重试。
5. 顺序执行工具，保存真实结果。
6. 更新重试状态，回到下一轮模型请求。

`enqueueTask` 只校验输入、固定提交时的配置与工具、非阻塞入队，不写聊天记录。忙碌不再是错误；队列满、输入为空、应用取消或会话关闭才拒绝提交。
任务执行失败会显示错误并结束本项，消费循环继续处理下一项；取消排队项不会写入模型历史。

`RunTask` 返回时通过 defer 调用 `finishTask`，统一写入成功/失败/停止状态；这是退出清理，不参与业务步骤调度。
管道输入独立放在 `pipe.go`：同样入队，然后等待 `job.done`，执行结束再读取下一行，避免 EOF 导致任务提前取消。
管道中的帮助、会话列表直接输出文本，配置菜单和无参数恢复会话给出使用提示；这些差异只在管道入口处理。

| 文件 | 职责 |
| --- | --- |
| `app.go` | 初始化、交互输入主循环、退出清理 |
| `pipe.go` | 独立的管道入口：逐行读取、同步执行和文本输出 |
| `commands.go` | 注册命令、查找 handler；主循环直接调用 `command.Handler(a, args)` |
| `command_handlers.go` | 创建、切换、恢复、停止、退出和配置操作，handler 只返回 error |
| `workspace.go` | 管理打开的会话和当前会话入口，防止重复打开历史记录 |
| `session_grid.go` | 渲染会话栅格和状态图标，只读取快照，不控制任务 |
| `tasks.go` | 一次任务的参数、入队和结束清理 |
| `terminal.go` | 读取当前会话的草稿和显示快照，保持输入可用；不启动业务 |
| `agent.go` | `Session.RunTask` 的完整顺序执行流程与 Python 有限重试 |
| `session.go` | Session 字段、唯一的消费循环、停止当前任务并清空队列 |
| `session_display.go` | 读取显示快照和更新界面消息，不调度任务 |
| `session_history.go` | 创建记录和把历史转换为显示内容，不调度任务 |
| `tools.go` | 工具调用及输出格式化 |

`App.CurrentSession` 是唯一的当前会话入口，`App.config` 是应用唯一的运行配置。`App.enqueueTask` 读取它并固定本次执行参数；Session 不接收配置。客户端和响应流只在 `RunTask` 发起请求的位置创建，不经过新建、恢复或切换会话的参数链。
切换时只更新这个指针。后台任务始终操作启动时的 Session，并使用 job 中的配置快照。
界面只交出输入和显示状态；命令查找和任务提交由主循环负责，执行顺序由各会话的 Run 循环负责。

## 这些结构体和状态有什么用

只有三个相关的数据结构，字段旁都有具体说明：

| 结构体 | 表示什么 | 存放位置 |
| --- | --- | --- |
| `Session` | 一个聊天窗口，保存聊天记录、草稿、当前任务和显示状态 | `session.go` |
| `task` | 这个窗口里一次提问的执行，保存模型参数、停止信号和结束通知 | `tasks.go` |
| `sessionSnapshot` | 从 Session 复制出来给界面排版的数据，不持有文件或客户端 | `session_display.go` |

`Session.history` 保存发给模型的上下文并写入 JSONL；`Session.messages` 是界面显示内容，会过滤内部提示词，也会加上错误等运行提示。
`streamText` 是“还没生成完的回答”，`progressText` 是“现在正在做什么”。完整回答到达后清空 streamText，避免同一回答显示两遍。

一次提问的状态变化：

1. `enqueueTask` 将 job 放进队列；`pending` 保留等待项供显示和取消，此时不写聊天历史。
2. `Session.Run` 取出 job，设置 `active = job`；`RunTask` 保存提问，随后请求模型并更新显示。
3. `finishTask` 设置 `active = nil`，记录成功/失败/停止，并关闭 `job.done` 通知本项等待者。消费循环随后取下一项。
4. 用户查看会话时，`markRead` 清除“有新结果”的提示；它不读取文件，也不启动任务。

`mu.Lock()` / `Unlock()` 保护界面和后台同时访问的内存状态。例如不能让界面在后台更新状态一半时读取。
`close(job.done)` 只通知本项已结束；`workerDone` 通知整个会话消费循环已退出。`App.Close` 先关闭入队入口、取消当前及等待任务，再等 `workerDone`，最后关闭聊天文件。
`pending` 还覆盖“刚被 channel 取走、还没标记 active”的短暂阶段，因此 `/stop` 不会漏掉这个任务。

独立字段采用逐行赋值，结构体初始化每个字段单独一行；`value, err := function()` 等函数多返回值仍使用 Go 的常规写法。

## 并发边界

每个会话只有一个消费 goroutine，每个任务有独立的 context 和完成通道。模型与工具按顺序执行。
任务直接更新本会话的状态，没有中转消息的 channel 或额外收集协程；打开帮助或配置菜单也不阻塞任务。
done 通道只通知“任务已经结束”，不传递模型输出。

后台更新的状态由每个会话自己的 mutex 保护。界面取快照读取，草稿只由界面线程编辑。
这里的锁只保护程序自己的内存状态，**没有为共享项目文件增加锁、隔离目录或冲突控制**。

切换不会取消任务。`/stop` 取消当前会话的执行和等待任务，其他会话继续运行；程序退出时先取消所有任务、等待消费循环结束，再关闭所有记录文件。
后台执行仅指 CLI 进程仍运行时；不支持关闭程序后继续执行，也不从历史文件自动重启旧任务。

## 配置

`/config` 编辑并保存应用的统一配置。修改后所有会话新提交的任务都使用新值，切换会话不会恢复旧配置；已经排队或运行的任务使用提交时的参数。
改变目录会创建并切换新会话，旧会话及任务保留。旧会话继续追加到已经打开的记录文件；切回后发起的新任务使用当前工作目录，模型请求中的系统提示词也随之更新。
